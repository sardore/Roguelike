# 도메인 모듈 분할 계획 (승인 요청)

> 코드는 아직 한 줄도 옮기지 않았다. 아래 계획을 승인받은 뒤에 시작한다.

## 1. 실측 (`node tools/refactor/domain-report.mjs`)
- 런타임은 최상위 문 3,638개: 함수 2,381 · const 571 · let 61 · 선언이 아닌 실행 문 662.
- 이름 규칙과 참조 관계로 선언을 나눈 대략의 크기:

| 도메인 | 선언 수 | 줄 수 | 다른 도메인이 쓰는 이름 (공개 면적) |
|---|---:|---:|---:|
| mapgen (층 생성·분기·지형 규칙) | 935 | 6,092 | 480 |
| render (그리기·스프라이트·카메라·FX) | 542 | 4,853 | 248 |
| ui (HUD·패널·입력·스토리) | 516 | 4,366 | 328 |
| monster (정의·스폰·AI·보스) | 363 | 2,375 | 249 |
| save (세이브·생명주기) | 134 | 910 | 83 |
| items | 239 | 818 | 186 |
| combat | 188 | 817 | 155 |
| kernel (state, TT, COLS/ROWS, k, 난수·해시, 거리 등) | 24 | 587 | 24 |
| 미분류 | 72 | 237 | 2 |

- 모든 도메인이 kernel을 크게 참조한다(예: mapgen→kernel 7,967, render→kernel 5,574, ui→kernel 5,002). `state` 하나만 1,483곳에서 쓰인다.
- 도메인끼리도 많이 얽혀 있다(ui→mapgen 614, mapgen→render 386 등). 지금은 순환이 있고, 함수 선언은 호이스팅되어 문제가 없다.
- **초기화 순서 제약**: 로드 중에 실행되는 `const`/`let`/실행 문이 앞서 정의된 `const`/`let`을 읽는 경우가 797곳이다. 도메인별로 파일을 나누면 실행 문의 상대 순서가 바뀔 수 있어 TDZ 오류(예: F-01의 `BRANCH_DEFS105`)가 난다. 파일 순서는 이 제약을 도구로 검증해서 정한다.
- 버전 접미사 함수 1,967개 중 **1,803개(92%)는 접미사만 떼도 이름이 겹치지 않는다.** 나머지 164개(이미 쓰는 이름 97, 같은 이름을 공유하는 버전 쌍 61, 너무 짧음 6)는 역할 이름이 필요하다 (`setIntent54`/`setIntent61`, `room59`/`room88`/`room47`, `repair43`/`repair44` 등).

## 2. 선택해야 하는 것 (권장안 A)
**A. 한 클로저 유지, 빌드가 도메인 파일을 이어 붙인다 (권장)**
- `src/game/` 아래에 도메인 파일을 두고 빌드(`tools/build.mjs`)가 순서대로 이어 붙여 지금과 같은 단일 IIFE 하나를 만든다.
- 장점: 61개 공유 `let`(`state`, `COLS`, `ROWS` 등)과 실행 순서가 그대로라 동작 보존이 쉽고, 단일 HTML·앱 결과가 지금과 기능상 같다. 이어 붙인 결과 파일의 구조 지표(재대입 0 등)는 지금과 같게 검사한다.
- 단점: `src/`를 브라우저로 바로 열 수 없다. 개발은 `npm run build:qa`(감시 모드 추가) 결과로 한다. 테스트는 이미 `dist-qa`를 쓴다.
- 경계 강제: 도메인마다 `public` 목록을 두고 `npm run check`가 "다른 도메인의 비공개 이름 참조"를 센다. 처음 목록은 현재 참조에서 자동으로 만들어 동작이 안 바뀌고, 이후 래칫으로 줄인다.

**B. 클래식 스크립트 여러 개 (IIFE 제거)**: 파일마다 `<script>`로 불러오고 최상위 `let/const`가 전역 렉시컬 스코프를 공유한다. `src/`를 바로 열 수 있지만 `function open/close/name` 같은 이름이 `window`를 덮을 위험이 있어 전체 이름 감사가 먼저 필요하다.

**C. ES 모듈**: `state`·`COLS` 등 재대입되는 공유 `let`을 접근 함수로 바꿔야 하고 순환 import 문제가 생긴다. 변경 폭이 가장 커서 권하지 않는다.

## 3. 파일 목록 (안)
```
src/game/
  00-kernel.js      state, TT, COLS/ROWS, 난수·해시·거리, 공용 헬퍼 (~600줄)
  10-world.js       지형 변경, 점유, 배치, 도달성, 시야 서비스
  20-mapgen.js      일반 층 생성, 건축, 검증
  21-special.js     23·24층, 소문 공간, 전설 던전, 열쇠·문
  22-branches.js    창해 용궁, 흑성채, 도장, 수로, 식량창고, 산채, 광산, 흑산채
  30-monsters.js    정의, 스폰, 역할 AI, 소리 AI, 보스 패턴
  40-combat.js      공격·피해·상태이상·무술·원소
  50-items.js       아이템, 부적, 포션, 음식·요리, 식별·저주
  60-render.js      지도·지형·스프라이트·FX·카메라
  61-sprites.js     몬스터·직업·아이템 그림
  70-ui.js          HUD, 패널, 토스트, 조사, 도감
  71-input.js       입력 라우터, 데스크톱·모바일 클라이언트
  72-story.js       스토리, 엔딩, 튜토리얼
  80-save.js        세이브 서비스, 생명주기, 이어하기
  90-boot.js        시작
```
도메인 하나가 약 1,000~3,500줄이 되도록 mapgen·render·ui는 둘 이상으로 나눈다.

## 4. 의존 방향 (목표)
`kernel ← world ← {mapgen, monsters, combat, items} ← {render, ui, story} ← save ← boot`
render는 상태를 읽기만 하고, 규칙 도메인(monsters·combat·items)은 render·ui를 부르지 않는다. 지금은 이 방향을 어기는 호출이 많아(ui→mapgen 614 등) 첫 공개 목록은 현재 관계 그대로 만들고, 위반 수를 래칫으로 줄인다.

## 5. 진행 순서와 한 도메인의 작업
순서(위험이 낮은 것부터): kernel → save → items → combat → monsters → render → ui/input/story → mapgen/special/branches → boot.
도메인 하나가 하나의 커밋이다.
1. 그 도메인의 버전 접미사를 떼는 기계적 이름 바꾸기(도구, 이름이 겹치면 역할 이름 — 사람이 지은 이름은 `docs/NAMING.md`에 옛 이름→새 이름으로 기록).
2. 선언을 새 파일로 옮기고, 실행 순서 제약을 도구로 검증.
3. `public` 목록 작성.
4. `npm run check` + `npm test`(기준선 133 + release) + 단일 HTML·앱 빌드 확인 후 커밋.

## 6. 승인받고 싶은 것

- [ ] `src/`를 바로 열 수 없게 되는 것(개발은 빌드 결과로)을 받아들이는가.
- [ ] 접미사를 떼서 생기는 이름이 지나치게 일반적인 경우(`room`, `app`, `carve` 등)는 역할 이름으로 바꾸고 `docs/NAMING.md`에 쓴다.
