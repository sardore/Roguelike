작성: 2026-10-26, 기준: main `8621ba3`(PR #34 병합 뒤). 이 문서는 **승인 전 계획서**다. 코드는 한 줄도 바꾸지 않았다. 아래 "확인이 필요한 것"에 답을 받기 전에는 1단계에도 들어가지 않는다.

## 1. 분기 정의 표와 입장층 계산

**현재**
- 분기 정의: `BRANCH_DEFS105`(branches.js:2193). 항목마다 `{name,count,parent,parentBranch?,parentLevel?,titles,color}`. 입장층은 이미 `parent`로 적혀 있다(canal 2, granary 3, stockade 7, palace 9, dojo 12, citadel 16; mine·black은 `parentBranch:'stockade'`).
- **입장층 표가 정의 밖에 한 번 더 하드코딩**되어 있다: branches.js:247 `{2:'canal',3:'granary',7:'stockade',9:'palace',12:'dojo',16:'citadel'}[state.floor]`, ui.js:391 `[2,3,7,9,12,16].includes(state.floor)`(불러온 세이브에 입구가 없을 때 보정). 입구 생성은 mapgen.js:2455의 `branchEntrance()`(일반 생성기의 마지막 단계)가 한다.
- `parent`를 읽는 곳(전부 정의에서 읽음): branches.js:137 `branchRootFloor`, 179 `branchCombatFloor`, 273 분기 상태의 `floor`, 761 위쪽 포탈, render.js:3328 색.
- 분기 만드는 곳은 `buildBranchPage`의 삼항 연쇄다: branches.js:298(지도 크기), 301(`buildPalace`/`buildCitadel`/…).

**설계**
- 입장 표를 지우고 정의에서 거꾸로 계산하는 함수 하나를 둔다: `branchEntranceId(floor)` = `parent===floor && !parentBranch`인 정의의 id(없으면 null), `branchEntranceFloors()` = 그 `parent`들의 집합. branches.js:247과 ui.js:391이 이것을 쓴다.
- 현재 값과 같음은 시험으로 고정한다(6개 층 ↔ 6개 분기 일치, mine·black 제외). 이 단계는 동작을 바꾸지 않는다.
- 분기 지도 크기·빌더의 삼항 연쇄도 같은 단계에서 정의 쪽 필드(`size`, `build`)로 옮기는 안을 제안한다. 안 옮기면 용암궁이 연쇄에 한 항을 더 붙이게 된다(덧붙이기). 옮기면 영향 범위가 branches.js:296~301 한 곳이다.

**영향 범위(측정)**: `'palace'` 문자열 52곳, `'citadel'` 35곳, `'dojo'` 21곳. 이 가운데 입장·정의에 걸린 것은 위 4곳이고, 나머지는 각 분기 고유 규칙이다(손대지 않는다).

## 2. 22층에 입구를 확정으로 놓는 방법

**22층의 사실**
- 황금 신전 위쪽 + 거울 미로 아래쪽, 세로 119칸으로 늘린 특수층이다(special.js:998 `build22_`). 3칸 폭 순례 통로가 필수 경로이고 마지막에 판다.
- 적 예산이 고정이다: monsters.js:1809 `floor22-final-budget-r43`은 22층에 한해 일반 +30% 밀도 보정을 건너뛴다. `TARGET61`의 22층 값은 43(monsters.js:2202), `SPECIAL_BASE_COUNTS[22]`는 15(monsters.js:2168). 입구는 몬스터를 만들지 않으므로 예산에 직접 닿지 않는다.
- `branchEntrance()`(mapgen.js:2455)는 건축 적용(`applyArchitecture1020`)·늦은 아이템 보정 **뒤**에 돈다. 후보 칸은 `playerSearch(unlock, openBoss)`로 닿는 칸 중 계단에서 4칸 이상 떨어지고, 점유·아이템이 없고, 4방향 중 하나가 통행 가능한 곳이다(branches.js:249~254).

**입구 확정 출현**
- 22를 정의의 `parent`로 두면 §1의 함수가 22를 인정하고, 같은 `branchEntrance()`가 22층에서도 돈다. 새 입구 코드를 만들지 않는다.
- 충돌 가능성(읽은 것, 아직 시험하지 않음): ① 후보가 필수 순례 통로 위일 수 있다 — 포탈 칸은 통과 가능한 표식이라(branches.js:2138의 주석과 `return false`) 통로를 막지 않는다. ② 22층 아이템·몬스터 재배치(mapgen.js:2906~2909 `restoreEntities1020`)가 입구 칸을 덮을 수 있는지 확인이 필요하다(입구는 그 뒤에 놓이므로 순서상 안전해 보이나, 시험으로 확인한다). ③ 입구가 없을 때: `required` 기본값이 참이라 후보가 없으면 `Error`를 던진다(branches.js:255). 호출이 생성 루프의 `try`(mapgen.js:2434 이하) 안이라 재시도로 이어지는 것으로 읽었지만 **확인하지 않았다**. 22층에서 후보가 없을 확률도 측정하지 않았다.
- **이미 22층에 있는 세이브**: ui.js:391의 보정이 22를 포함하게 되므로, 22층에서 불러온 옛 세이브에 로드 시 입구가 생긴다(이미 지나온 층에 포탈이 생기는 동작 변경). 선택지: (가) 그대로 허용 (나) `branchEntrance`가 세이브 버전으로 22층 소급을 막는다. 질문 3.

## 3. 분기 깊이(4~7), 전투층, `scaledMonster`

**깊이 굴리기(요청문 3번)**
- 위 §0-C대로 기존 "`branchDepth` 방식"은 없다. 제안: `citadelEnsurePlan` 모양을 따라 `branchWorld105.lavaPalace105 = {depth}`를 **런 시작(`newGameCoreLifecycle`)에 한 번** 굴려 저장하고, 옛 세이브는 `branchUnpackWorld`(branches.js:91)가 같은 함수를 불러 보정한다.
- 굴림은 `RngService.shop(`${runId}|lava-depth`)`처럼 **런 ID로 시드**한다(palace가 이미 이렇게 한다, branches.js:439). 그러면 저장 필드가 없어도 같은 런에서 같은 값이 나와, 옛 세이브·저장 문자열 가져오기(`docs/SAVE_STRING.md`)와도 충돌하지 않는다. 저장은 "한 곳에서 계산·보관"일 뿐 출처가 둘이 되지 않는다.
- `BRANCH_DEFS105`의 `count`는 지금 고정 숫자이고 읽는 곳이 3곳이다(branches.js:177 안내 문구, 295 층 번호 검증, 1034 다음 층 포탈). 용암궁은 `count`를 최대값(7)으로 두고, 실제 층수는 `branchLevelCount(id)` 한 함수가 돌려주게 하고 위 3곳을 그 함수로 바꾼다.
- `branchPruneWorld`(branches.js:154)는 뿌리 층이 현재 층보다 낮은 분기 페이지를 지운다. 용암궁의 뿌리는 22층이라 23층으로 내려가면 페이지가 정리된다(다른 분기와 같다). 확인만 하고 바꾸지 않는다.

**전투층(요청문 4번)**
- `branchCombatFloor`(branches.js:179) = `입장층 + 레벨`(citadel만 `25-3`). 용암궁은 22+1 … 22+7 = 23 … 29가 된다. `scaledMonster`(monsters.js:38)는 상한을 두지 않는다(식에 `min`이 없다. `Math.min(25`·`clamp(…,25)` 검색 결과 없음).
- **측정(계산)**: 월화 궁수(기본 HP 44)의 배율은 전투층 23 → ×1.69(HP 74), 25 → ×1.83(HP 81), 26 → ×1.63(HP 71), 29 → ×1.84(HP 81)이다. 식의 `within=(층-1)%5` 때문에 **5층마다 배율이 톱니처럼 떨어진다**(25→26에서 감소). 상한 없이 7레벨을 쓰면 레벨 3(전투층 25)이 레벨 4(26)보다 세다. 이것이 의도인지는 질문 4. 요청문대로 "수치가 아니라 메커니즘으로 난이도를 만든다"면 이 톱니를 그대로 두어도 레벨 간 체감은 평평하다(HP 71~81).
- `state.floor`는 분기 안에서 22로 남으므로 `tierForFloor`(items.js:1008) 등 `state.floor`를 읽는 보상 계산은 전투층이 아니라 22층 값을 쓴다. 이것도 다른 분기와 같다.

## 4. 설계 제안

### 4.1 열 상태 하나로 통합

**용어**: 열 그룹 = 같이 움직이는 용암 타일 묶음. 그룹마다 기록 하나, 모든 파생 효과는 이 기록에서 계산한다.

```
branchTerrain105.lava105.groups[id] = {
  cells: [[x,y], …],          // 생성 때 고정(지형 기록과 같은 소유)
  phase: 'hot' | 'quenched' | 'cracked',
  left: 남은 턴(감소 카운터),  // 절대 턴이 아니라 남은 턴: 다른 페이지에 가 있는 동안 멈춘다
}
```

- **전이**: `hot` →(냉기 접촉) `quenched`(left=7) → left가 2 이하가 되면 `cracked` → left 0이면 `hot`. `cracked`일 때 냉기 접촉은 무시(갱신 불가). `quenched`일 때 접촉하면 `left`를 7로 갱신할지는 질문 5(요청문은 "균열 단계에서만 갱신 불가"라고 해서 갱신 가능으로 읽었다).
- **타일 쓰기**: 그룹 기록이 유일한 원본이다. 지도 타일은 phase의 결과로 `RuntimeTerrainOwner.mutate`(monsters.js:1464)로 쓴다. 기존 `RuntimeTerrainOwner.temporary`(칸마다 TTL 기록 `tempTerrain74`)는 **쓰지 않는다**: 칸별 타이머는 "별도 타이머·복사본 금지"에 걸린다. 얼음(`freezeWater105`)은 현재 칸별 TTL이므로 그 경로를 용암에 재사용하면 안 된다.
- **새 타일**: `TT.QUENCHED_ROCK`(급랭암) 하나. `quenched`와 `cracked`는 같은 타일이고 균열 모양은 그리기에서 그룹의 phase를 읽어 덧그린다. 얼음 `TT.ICE`는 재사용하지 않는다. 용암 타일은 기존 `TT.LAVA`다.
- **즉사**: 뜨거운 그룹의 용암 타일은 기존 용암 사망 경로(monsters.js:2083, `hazardTile` monsters.js:2161)가 그대로 처리한다. 급랭암 위에 서 있을 때 그룹이 `hot`으로 돌아가면, 타일이 `TT.LAVA`로 바뀌는 순간 `mutate`가 점유자에게 `revalidateAt`(위험 재검사)을 걸어 즉사시킨다(monsters.js:1481 부근의 기존 동작). 즉 "균열 2턴"이 플레이어의 경고 시간이다.
- **파생 효과**(통행 여부, 열기 균열, 열팽창 격벽)는 `lavaGroupPhase(id)` 한 함수에서 묻는다. 소비자가 phase를 복사해 두지 않는다. **"열기 균열"과 "열팽창 격벽"이 정확히 무엇인지 요청문에 풀이가 없다** — 아래 해석을 가정으로 쓴다(질문 6): 열기 균열 = 뜨거운 그룹 가장자리 바닥이 갈라져 접촉 피해를 주는 칸, 열팽창 격벽 = 그룹이 뜨거울 때 닫히고 식으면 열리는 벽(경로 차단용).
- **적연(플레이어 무기)과의 상호작용**: 적연은 죽인 자리 3×3을 5턴 임시 용암으로 바꾼다(`tempLava47`, monsters.js:2335). 그 임시 용암을 그룹 칸이나 급랭암 위에 쓰는 것은 막아야 한다(그룹이 유일 원본). 규칙: 그룹 칸에는 임시 용암을 쓰지 않는다. 시험 항목에 넣는다.

### 4.2 서리압 분사기 (냉기 → 그룹 급랭)

- 분사기는 **원격 장치**다. 기존 원격 작동 구조(`mine105` 단추·벽·원격 열쇠, `pressureSwitchVariant105`, branches.js:2085, `citadel105.opened[remote105.key]`)를 쓴다: 단추가 눌리면 분사기가 목표 칸들에 `emitElementContact105('ice', cells, …)`를 한 번 낸다. 새 작동 시스템을 만들지 않는다.
- 그룹 급랭은 **접촉 표의 항목**으로 들어간다(§0-D의 정리 뒤): `{elem:'ice', 대상:'열 그룹의 용암 타일', 효과:lavaGroupQuench}`. 그룹 기록이 없는 용암은 표에 걸리지 않는다(§0-E).
- 플레이어의 냉기 수단(냉기 부적·빙결 각인 무기)도 같은 접촉 표를 타므로, 용암궁 안에서는 분사기 없이도 그룹을 얼릴 수 있다. 이것이 의도인지 질문 7(분사기만으로 제한하려면 접촉 표 항목에 `source` 조건이 필요하고, 그러면 표에 특수 조건이 생긴다).

### 4.3 군단장 (전용 몹, 순회) — 같이 결정해야 하는 부분

**기존 부품(읽은 것)**

### 4.4 맵 구조 (나선 금지)

- 방 그래프를 먼저 만들고 타일은 그 위에 그린다. 방 그래프의 조건(검증기가 확인):
  1. 독립 순환로 4개 이상(순환 수 = 간선 − 노드 + 1 ≥ 4, 서로 간선을 공유하지 않는 순환 4개)
  2. 입구→중앙 사대 최단 경로 ≥ 직선거리 × 3
  3. 보상이 있는 막다른 가지 2개 이상
  4. 원격 작동이 필요한 구간(분사기로 그룹을 얼려야 지나는 구간) 1개 이상
  5. 모든 칸 도달 가능성(분사기 작동 전 도달 가능한 영역과 작동 후를 따로 계산)
- **생성**: 시드 → 방 배치(격자 위 최소 간격) → 신장 트리 → 순환용 간선 추가 → 막다른 가지 부착 → 용암 그룹 배치(한 그룹이 한 구간을 가로막음) → 분사기·단추 배치(그룹과 **다른 순환로** 쪽) → 검증. 실패하면 시드에 시도 번호를 더해 재시도, **최대 16회**(`mine`·`canal`·`granary`와 같은 상한, branches.js:287). 그래도 실패면 오류(생성 실패 처리는 기존 분기와 같다).
- 지도 크기와 페이지 저장: 팔레스(123×123, 131×131)와 흑성채(241×241) 사이를 목표로 한다. 레벨마다 페이지 하나이고 입장 시 생성한다(다른 분기와 같다). 7레벨 × 최대 16회 재시도의 생성 시간은 **측정하지 않았다**(1단계에서 측정하고 상한을 정한다).
- **타일·장식 퀄리티(용궁 이상)**: 용궁은 빌더 한 개가 방 6종·높이 4단계·창·소품·타일 설명을 자기 안에 가진다(`buildPalace`, branches.js:437~, 렌더 `drawPalaceCell` render.js:3296, 용궁 코드 branches.js 133곳·render.js 22곳). **이 방식을 복제하지 않는다**(병렬 신설). 용암궁은 "방 테마 8개 이상, 높이 단계 3개 이상, 타일마다 조사 문구·미니맵 색·그리기·통행 규칙"을 **표 하나**(테마 표, 타일 표)에서 읽게 만들어, 빌더·그리기·조사 문구·미니맵이 같은 표를 읽는다. 용궁을 이 표로 옮기는 것은 이번 범위가 아니다.

### 4.5 보상: 최종 레벨 중앙 사대에서 적연

- 최종 레벨(깊이 4~7 중 마지막) 중앙에 "사대"(활터) 방을 두고 거기서 적연을 준다. 선례: `water_crossbow`는 "창해 용궁 · 잠긴 조정"에서 `artifactReward46`으로 나온다(branches.js:2479 부근의 전설던전 보상 놓기를 용궁이 `claimed47`/`possesses47`로 중복 방지). 용암궁 보상도 같은 중복 방지(이미 소유·획득 이력이 있으면 지급 안 함)를 쓴다.
- 적연은 **무기 정의를 남긴다**(`LEGENDS47`의 `lava_bow` 항목: 능력 `용암 장례`, `weaponElement105`가 `fire`로 읽음 elements.js:30, 아이콘 render.js:2846·4318, 능력 구현 monsters.js:2307·2335). 지우는 것은 **던전 부분**이다(§5-5).
