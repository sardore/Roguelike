# 플레이 데이터 수집 조사: "플레이어들이 어디서 죽는가" (코드 변경 없음)

작성: 2026-10-26, 기준: main `8621ba3`. 이 문서는 **조사**다. 수집 코드는 한 줄도 넣지 않았다. "확인함"은 코드를 읽거나 검색한 것, "확인 안 함"은 말 그대로 확인하지 않은 것이다.

## 결론

**가능하다.** 기록할 지점은 코드에 이미 하나로 모여 있다. 없는 것은 전송 경로(서버)다. 지금 게임에는 네트워크 코드가 없고 호스팅은 정적 페이지라, 데이터를 받을 곳을 **새로 정해야 한다.** 그 선택(외부 계정·서비스·비용)은 제가 할 수 없고 정하셔야 한다.

## 2. 무엇을 수집할 수 있나 (사망 시점에 코드에서 읽을 수 있는 값)

- 층(`state.floor`), 분기(`branchContext105`의 `id`·`level`), 전설던전(`artifactDungeon46`의 `id`), 상점 중간층 여부
- 직업(`player.classId`), 레벨, 처치 수, 턴 수, 최대 HP, 장비 종류
- 원인: `die(by)`의 `by` 문자열(몬스터 이름 또는 환경 원인 예: `용암`)
- 사망 좌표(`player.x`, `player.y`), 빌드 버전(`RELEASE_INFO.build`), 런 ID(무작위 UUID)
- 사망 직전 로그 몇 줄(자유 텍스트. 용량·내용을 제한해야 함)

**"어디서"의 해석에 주의**: 특수층(2·4·6·8·11·13·16·18·20·22~25층)은 지도가 고정이라 좌표를 모아 히트맵을 그릴 수 있다. 일반 층은 런마다 지도가 달라 **좌표가 의미가 없다.** 그쪽은 (층, 원인 몬스터, 직업, 레벨, HP, 직전 행동) 조합이 더 쓸모 있다. 분기(용궁, 흑성채, 도장 등)는 층 수와 별개로 `분기 id + 레벨`로 모으는 것이 맞다.

## 3. 받는 쪽 방안 (장단점. 가격·한도는 **조사하지 않았다**)

| 방안 | 방식 | 장점 | 단점 / 위험 |
|---|---|---|---|
| A. 서버 없이 수동 제출 | 사망 기록을 로컬에 쌓고, 설정 패널의 "기록 복사"로 텍스트를 만들어 사용자가 디스코드·폼에 붙여넣는다. 이미 있는 저장 문자열 방식(`docs/SAVE_STRING.md`)과 같은 모양 | 서버 불필요, 개인정보 부담이 가장 작다, 먼저 시작 가능 | 자발적 제출이라 표본이 매우 적고 한쪽으로 쏠린다 |
| B. 익명 자동 전송 | 사망·승리 때 작은 JSON을 외부 엔드포인트로 POST. 엔드포인트 후보: 구글 Apps Script 웹앱+시트, Cloudflare Workers+저장소, Supabase/Firebase, PostHog 같은 분석 서비스의 사용자 정의 이벤트 | 표본이 크다, 집계가 쉽다 | 외부 계정·배포·비용이 필요(제가 대신 못 함). 요청 형식·응답 읽기 제한은 서비스마다 다르다(확인 안 함). 개인정보·동의 문제 |
| C. 미리 채운 GitHub 이슈 링크 | 사용자가 누르면 내용이 채워진 이슈 작성 창이 열린다 | 서버 불필요 | 공개 저장소에 공개되고, 번거로워 거의 아무도 안 낸다. 추천하지 않음 |

추천: **A로 시작해 데이터 모양(스키마)을 굳히고, 동의 화면과 함께 B를 붙인다.** B의 받는 곳은 먼저 정해져야 한다.

## 4. 개인정보와 동의 (코드 이전에 정할 것)

- **동의 방식**: 설정 패널의 토글(기본 꺼짐, 첫 사망 때 한 번 묻기)을 제안한다. 동의 없이 보내는 것은 권하지 않는다.
- **식별자 금지**: 장치 ID, 계정, 이름, 광고 ID는 보내지 않는다. 런 ID는 무작위 UUID라 사람과 연결되지 않지만, 같은 사람의 런을 묶을 수 있는 영구 ID는 만들지 않는다.
- **IP**: 받는 서버는 요청을 보낸 IP를 볼 수 있다. 엔드포인트가 IP를 저장하지 않게 설정해야 한다(서비스별 설정, 확인 안 함).
- 자유 텍스트(로그)는 개인 정보가 들어갈 여지가 있어 넣지 않거나 고정 문구만 넣는다.
- 한국 개인정보보호법 등의 해당 여부는 **저는 법률 검토를 할 수 없다.** 익명·비식별 집계라도 공개 전에 확인하시길 권한다.
- 앱스토어·플레이스토어에 올리는 경우 각 스토어의 데이터 수집 신고가 따로 있다(확인 안 함).

## 5. 이 저장소의 규칙에 맞는 구현 모양 (승인 시)

1. 수집 항목을 만드는 함수와 보내는 함수를 **하나의 소유자**에 둔다. 사망 지점 `die`를 감싸지 않고, **런 종료 효과 표에 항목 하나를 추가**한다(감싸기·재대입 금지 규칙).
2. 전송 실패·오프라인은 로컬 큐에 최대 N건 쌓았다가 `online` 이벤트나 다음 실행 때 보낸다(타이머를 늘리지 않는다: 구조 지표 `timer`는 40 상한).
3. 새 localStorage 키(동의 값, 큐)는 **저장 형식을 바꾸지 않는 추가**지만, 저장 문자열(`SAVE_STRING`)에 실려 다른 기기로 번지지 않게 제외 목록에 넣는다. 세이브 호환(`saveVersion`)은 건드리지 않는다.
4. 시험: 헤드리스에서 `fetch`를 가로채 보내는 내용을 검증한다(동의 꺼짐이면 0건, 켜짐이면 스키마와 일치, 오프라인이면 큐). 새 시나리오가 생기므로 값 기준선은 의도한 변경으로 기록한다.
5. 큐 키·동의 키 때문에 `values`·`saves` 기준선이 바뀔 수 있다. 의도한 변경으로 구분해 적는다.

3. **수집 항목**: §2에서 뺄 것과 더할 것. 특히 사망 좌표와 로그를 넣을지.
