# 관전 기능 계획 (코드 변경 없음, 승인 대기)

작성 2026-10-28. 이 문서는 조사와 계획뿐이다. 아래 "결정할 것"에 답이 나오면 1단계부터 만든다.

## 0. 무엇을 만드는가 (확인 필요)

"관전"이 만루에서 뜻할 수 있는 것은 셋이다. 기본 가정은 **A**다.

| | 뜻 | 서버 | 비고 |
|---|---|---|---|
| A | 다른 사람이 하는 판을 실시간으로 본다 | 필요 | 메가리그의 관전과 같은 쓰임 |
| B | 끝난 판을 다시 본다(사망 재생) | 선택 | 기록 저장만 있으면 됨 |
| C | 지금 있는 디버그 전장 관전(`battleWatch57`)을 정식 기능으로 | 불필요 | 몬스터끼리 싸우는 모드 |

## 1. 이미 있는 것 (조사 결과)

- **같은 저자의 중계 서버**: `sardore/cp32-online-relay`(`server.js` 625줄, 의존성 없는 Node WebSocket, `/online`, 방 코드·큐·재접속 유예·목록 `browseClients`)와 `cp32-online-server`의 `render.yaml`(Render 무료 웹서비스, `/health`). 메가리그는 이걸로 방·관전자(`src/features/spectators.js`, 792줄: 관전 요청·이탈·채팅·관전자 수 알림)를 구현했다.
- **세이브 한 벌이 곧 화면 상태**: `SaveService.commit`이 행동마다 `GameState.project`로 상태를 직렬화한다. 1층 기준 72 KB, gzip 14.6 KB(층이 깊어지면 더 큼). `loadGameCore({state,settings})`는 저장소가 아니라 객체에서 불러오는 입구가 이미 있다.
- **저장을 건너뛰는 선례**: `state.debugBattle57`이면 `SaveService.request/flush`가 아무것도 쓰지 않고 돌아간다. 관전 상태도 같은 방식으로 막는다.
- **상태 없이 보이는 화면 선례**: 디버그 전장의 `battleWatch57`은 조작 없이 실제 렌더러로 전장을 그린다(`DEBUG_BATTLE57.watching`).
- **막힌 것**: 런타임 난수에 판마다 고정된 씨앗이 없다(`RngService.runtime()`). 그래서 "입력만 보내서 같은 판을 재현하는 방식"은 쓸 수 없다. 상태를 보내야 한다.
- Apps Script(통계 서버)는 요청에 응답만 하므로 실시간 전송에는 못 쓴다.

## 2. 구조 후보 (A 기준)

| | 방식 | 보내는 것 | 장점 | 단점 |
|---|---|---|---|---|
| **1** | **상태 스냅샷 전송** | 행동마다 세이브 객체(gzip) | 관전자가 직접 화면 구성(확대·이동), 코드 경로가 "이어하기"와 같음 | 대역폭(턴당 15 KB~), 모바일 부담 |
| 2 | 화면 영상 전송 | 캔버스 JPEG 또는 WebRTC | 게임 로직과 완전히 분리, 구현이 가장 쉬움 | 해상도·화면비 고정, 관전자는 아무것도 못 바꿈, 대역폭 큼 |
| 3 | 입력 재현 | 입력만 | 가장 가벼움 | 난수 고정이 없어 **불가능** |

**권장: 1(상태 스냅샷)**, 단 보낼 양을 줄인다.
- 층에 들어갈 때 전체 스냅샷을 한 번 보낸다.
- 턴마다 바뀐 최상위 키만 보낸다(`player`, `monsters`, `items`, `seen` 증가분, `log`, 바뀐 지형 칸). 정적인 큰 키(`decor`, `floorPattern1022`, `featureRooms` 등)는 층당 한 번.
- 턴당 1~3 KB를 목표로 한다. 그래도 크면 2(영상)를 보조 수단으로 둔다.

## 3. 단계

### 1단계 — 서버와 규약 (만루 코드 변경 없음)
1. `cp32-online-relay`를 만루용으로 복제해 `manru-relay`로 둔다(방 모드 `PVP`/`BOSS_COOP`을 `WATCH`로 대체, 방 안에 호스트 1·관전자 N, 호스트는 쓰기, 관전자는 읽기).
2. 메시지: `host.hello{runId,class,floor}`, `host.full{gz base64}`, `host.delta{turn,keys}`, `host.end{cause}`, `spec.join`/`spec.leave`, `room.list`(관전 목록: 직업·층·턴·관전자 수).
3. 호스트 인증: 방마다 무작위 토큰. 관전자는 방 코드만 있으면 읽기만 가능. 닉네임·계정 정보는 보내지 않는다(통계 정책과 같다).
4. 호스팅: Render 무료는 15분 무트래픽이면 잠들어 첫 접속이 30~60초 걸린다. 허용 여부를 정해야 한다(아래 결정 5).

### 2단계 — 호스트 쪽 (플레이어)
- 새 도메인 파일 `src/game/spectate.js`를 `manifest`의 `stats` 앞에 추가(**소유자 하나**: 연결·방·전송 모두 여기).
- 전송 시점은 `SaveService.commit`이 직렬화를 끝낸 자리 하나뿐(래핑·재대입 없이 그 함수 안에서 `Spectate.send(project)` 호출). 중복으로 직렬화하지 않는다.
- 켜고 끄는 곳: 설정 패널의 "관전 허용" 토글(기본 꺼짐), 켜면 방 코드를 보여 준다.
- 끊김: 소켓이 끊기면 판은 그대로 진행하고 재접속 때 전체 스냅샷을 다시 보낸다. 실패는 플레이에 영향을 주지 않는다(`ignoreError` 후 계속).

### 3단계 — 관전 쪽
- 진입: 타이틀에 "관전" 버튼 → 목록(방 코드 입력 또는 `room.list`).
- 상태 적용: 전체 스냅샷은 `loadGameCore({state,settings})`로, 델타는 상태 키 교체로 적용. 이 모드의 `state.spectator=true`.
- **쓰기 금지**: `state.debugBattle57`과 같은 자리에서 `state.spectator`일 때도 `SaveService.request/flush`가 아무것도 안 하게 한다. 입력(`InputRouter`)과 `ActionDispatcher`는 `state.spectator`면 이동·행동을 받지 않고 카메라·확대만 받는다. 통계 전송(`PlayStats.recordDeath`)도 막는다(관전 중 죽음이 기록되면 안 됨).
- 화면: 실제 렌더러를 그대로 쓴다. 호스트 시점 따라가기(기본)와 자유 시점 전환. 상단에 "관전 중 · 직업 · 층 · 턴 · 관전자 N".
- 종료: `host.end`를 받으면 사망 원인과 함께 마지막 화면을 남기고 목록으로 돌아간다.

### 4단계 — 부가
- 사망 재생(B): 호스트가 전송하는 스냅샷 열을 기기에 저장(최근 N턴 링 버퍼)하고, 사망 화면에서 "마지막 장면 보기"로 같은 관전 화면에 재생한다. 서버 불필요.
- 관전자 채팅과 응원은 만들지 않는다(필요 시 메가리그 `spectators.js`의 규약을 참고).

## 4. AGENTS.md 규칙과의 관계
- 소유자는 `spectate.js` 하나. 같은 일을 하는 두 번째 함수·상태 필드를 만들지 않는다.
- 저장 형식과 localStorage 키는 바꾸지 않는다. 관전 상태는 저장하지 않는다.
- `SaveService`의 쓰기 건너뛰기는 새 분기를 덧붙이는 게 아니라 기존 `debugBattle57` 조건을 "저장하지 않는 모드" 하나로 합치는 형태로 고친다.
- 모든 CSS는 `src/styles/`, `!important` 추가 없음. 서버는 `server/manru-relay/`로 분리하고 빌드 산출물에 넣지 않는다.
- 공용 로드 경로(`loadGameCore`, `restoreState`)를 건드리므로 일반 이어하기·세이브 복원·저장 후 이어하기·디버그 전장을 회귀 검사한다.

## 5. 검증 계획
1. 단위: 델타 적용 결과가 전체 스냅샷과 같은지(같은 판 30턴을 두 방식으로 만들어 해시 비교).
2. 브라우저 2개(Playwright): 호스트가 걷고 싸우고 층을 내려가는 동안 관전자의 화면이 일치하는지 스크린샷 비교, 호스트 소켓을 끊었다 붙였을 때 복구, 관전자가 `localStorage`에 아무것도 쓰지 않는지.
3. 부하: 관전자 10명 동시, 턴당 전송 크기·서버 CPU·모바일 배터리 확인.
4. 실제 폰 두 대(PC 아님)로 확인. 지금까지는 헤드리스만 확인했다.
5. 기존 기준선(`screens`, `values`)은 의도한 변경만 갱신하고 커밋 메시지에 적는다.

## 6. 위험
- 델타가 어긋나면 화면이 깨진다 → N턴마다 전체 스냅샷으로 재동기화.
- 관전자가 상태를 받아 보면 **미탐색 영역·몬스터 위치까지** 알 수 있다 → 필요한 만큼만 보내는 필터(관전자에게는 호스트의 `seen` 범위만)를 서버나 호스트에서 한다. 공개 방송이면 상관없으나 대결형이면 치팅 정보가 된다.
- 무료 호스팅 한도와 콜드 스타트.
- 세이브 직렬화에 들어 있지 않은 런타임 전용 값(연출·FX)은 관전 화면에 안 나오거나 어색할 수 있다 → 1단계 프로토타입에서 눈으로 확인.

6. 먼저 만들 범위: 1~3단계(실시간 최소 기능)부터, 4단계는 뒤로?
